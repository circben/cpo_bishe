# 第三章 系统架构设计

---

## 3.1 系统需求分析

CPO方法的全流程落地涉及数据准备、搜索执行、偏好提取、模型训练、效果评估和结果展示六个环节，任一环节的缺失都会令后续步骤无法推进。项目启动阶段首先面对的一个现实问题是：如何把各个独立的功能模块串联成一条可以端到端运行的管道，同时保持每个模块的独立性，方便单独调试和参数调优。

从功能层面看，管道需要依次完成以下事情。数据环节要解决原始数据集从哪里获取、怎样统一格式的问题——GSM8K和StrategyQA分属数学推理和常识问答两个场景，原始数据的字段结构和标注方式完全不同，需要各自处理后统一为相同的JSON结构。搜索环节是整个管道中计算量最大的部分：每个问题要调用大模型上百次，逐轮执行候选步骤生成、打分、剪枝、回溯，最终锁定最优推理路径；这个过程里产生的完整树结构不能丢弃，需要序列化保存下来，供偏好提取和后续可视化使用。偏好构建环节基于搜索树自动抽取步骤级偏好对，但并非树中所有节点都适合拿来训练——评分差距过小的分支区分度不足，语义高度重复的候选也不必同时保留，因此需要设置质量过滤和去重步骤。训练环节要同时跑两条线：CPO利用偏好对做对比式微调，TS-SFT把成功路径当作标准答案做监督微调；两条线必须共用同一个基座模型和LoRA配置，才能保证对比结论的可信度。评估环节需要测四种方案——SC-ToT搜索、标准CoT、TS-SFT模型和CPO模型——在GSM8K和StrategyQA两个数据集上的准确率与推理延迟，评估脚本的输入输出格式必须对齐，否则数据无法放在同一张表里比较。最后，搜索结果、性能指标和统计数据需要一种比表格和日志更直观的查阅方式，做成Web端的交互看板是合理的选择。

非功能方面有几个约束贯穿了整体设计。一是各阶段之间靠JSON/JSONL文件交接数据，不做过深的函数级耦合——阶段内部实现可以自由改动，只要输出文件的格式不变，上下游完全不受牵连。二是所有可调节的参数——束宽度、候选数、自洽性采样次数、学习率、LoRA秩、DPO的β值等——没有用额外的配置文件承载，而是以 Python dict 的形式直接写在每个阶段的管道脚本顶层（如 MINIMAL_CONFIG 和 ADVANCED_CONFIG 两个字典），日常切换任务或调参只需要改脚本前几行的几个键值即可；临时调整则通过 argparse 命令行参数覆盖，这种"脚本即配置"的做法省去了另一个需要单独维护的配置文件层，也让实验参数和调用入口始终绑定在一起。三是代码组织方式：核心算法统一放在src/cpo下按功能分子目录（tot/、train/、eval/、preference/、llm/），管道控制脚本统一放在scripts下按阶段分目录（stage1/～stage5/），便于按需定位到具体模块。

## 3.2 五阶段管道架构

管道按职责先后切为五个阶段，彼此之间只靠文件交接数据。下面这张简图概括了物料在五个阶段间的流动方向：

```
原始数据 → [Stage 1: 数据准备] → 标准化数据
标准化数据 → [Stage 2: ToT搜索 & 偏好构建] → 搜索树 + 偏好对
偏好对 → [Stage 3: 模型训练] → CPO模型 + TS-SFT模型
模型 → [Stage 4: 多基线评估] → 评估指标JSON
指标JSON + 搜索树 → [Stage 5: Web可视化] → 交互式Dashboard
```

### 3.2.1 Stage 1: 数据准备

项目选用了GSM8K和StrategyQA两个数据集，前者考察多步数值推理能力，后者侧重常识性问答中的多跳逻辑。两个数据集来自不同发布方，原始格式差异很大——GSM8K以JSON字典形式组织，StrategyQA则分散在多个JSON文件中且没有统一的训练/测试切分。Stage 1的任务就是把它们拉到本地，清洗成同一套schema。

`download_datasets.py`借用了HuggingFace datasets库的下载能力，把两个数据集拉取到`data/raw/`下保留原始副本，避免后续处理出错时还需要重新下载。`ingest_to_raw.py`是格式统一层：不管源文件长什么样，输出都规整为`{"question": "...", "answer": "..."}`这种最简单的键值对，字段只保留问答本身，不夹带任何与推理无关的元信息。`split_strategyqa.py`专门为StrategyQA做数据划分，因为官方发布时只给了全量JSON，训练和测试怎么分需要按固定比例在脚本里就地完成。整个阶段跑完以后，`data/`下会产出一批JSONL文件，Stage 2只认这些，不再依赖上游的任何临时产物。

### 3.2.2 Stage 2: ToT搜索与偏好数据构建

Stage 2是整个管道里计算最重、代码量最大的环节，一块负责搜索，一块负责从搜索结果里抽取训练数据。

搜索侧的入口是`run_stage2_pipeline.py`，它按Stage 1给出的JSONL逐条读取问题，分派给`run_preference_batches.py`做批量调度，每个问题最终由`run_preference_job.py`驱动跑一次完整的SC-ToT搜索。搜索算法本身落在`src/cpo/tot/`目录下：`sc_tot_search.py`实现了增强搜索的主流程，`bfs_search.py`提供按层展开的BFS遍历逻辑，`node.py`封装树节点的状态与元数据，`tree.py`维护全树的增删查改，`termination.py`根据答案确定性或深度上限判断某条路径是否该停止，`scoring.py`封装LLM打分调用，`concurrency.py`把同一层多个候选节点的评估请求并行发出去以减少整体等待时间。

搜索完成后进入偏好构建。`src/cpo/preference/extractor.py`从每棵搜索树中回溯所有到达正确答案的路径，沿路径逐个步骤生成"偏好后继 vs 非偏好后继"的对比对。这些原始偏好对还不能直接丢给训练——`quality_filter.py`会筛掉评分差距太小的对（差异不够大意味着模型学不到明确的偏好方向），`similarity_filter.py`则用嵌入相似度把语义几乎重复的候选合并掉，避免训练数据冗余。

Stage 2最终产出的两样东西都交到下游：序列化后的完整搜索树（`serialize.py`负责写入）留给Stage 5做可视化素材，过滤后的偏好数据JSONL交给Stage 3做训练原料。

### 3.2.3 Stage 3: 模型训练

Stage 3要同时养活两条训练线，它们的输入来源于同一批搜索树但走的路径完全不同。

CPO这条线的处理链是：`prepare_dpo_data.py`先读取Stage 2产出的偏好对，按DPO训练格式重新组织为`(prompt, chosen_step, rejected_step)`三元组——注意这里的粒度是步骤级而非完整回答级，每个三元组只对应推理链中的某一个决策点。`train_dpo.py`拿到数据后调用`src/cpo/train/dpo_trainer.py`启动DPO训练，底层使用的是TRL库的DPOTrainer封装，模型基座通过`model_loader.py`加载，LoRA的低秩适配矩阵由`lora_setup.py`配置并注入。

TS-SFT这条线相对简单：`train_ts_sft.py`直接拿搜索到的成功推理路径，把整条路径的完整文本当作监督目标，用标准交叉熵损失做微调——本质上就是让模型模仿那些被ToT搜索验证过的"好思路"。两条线的基座模型和LoRA配置完全相同，差别只在训练信号：一个是对比式的步骤偏好，一个是模仿式的路径监督。训练结束后各自产出一份LoRA适配器权重。

考虑到训练可能持续数小时，`run_cpo_screen.sh`和`run_ts_sft_screen.sh`包装了screen会话，避免因SSH断开导致训练中断，这是纯工程层面的保障措施。

### 3.2.4 Stage 4: 多基线评估

Stage 4的目标是把所有方法放在同一把尺子下量一遍。`run_stage4_pipeline.py`调度四路评估流程：SC-ToT搜索（训练前的在线搜索基线）、标准CoT（不经过任何微调的单路推理）、TS-SFT模型（路径监督微调后的结果）、CPO模型（步骤偏好微调后的结果）。评估维度有两个——准确率和推理延迟。

准确率方面，`metrics_gsm8k.py`对GSM8K的评估逻辑是：提取模型输出中最后一次出现的数值表达式，与标准答案进行精确数值比对；`metrics_strategyqa.py`对StrategyQA的判断则更灵活——题目本身是布尔型问答，只需把模型输出映射为True/False后与标签对照即可。延迟测量统一由`latency.py`负责：记录从prompt送入模型到最后一个token输出完成的时间，多次测量取平均，排除首次推理时的模型加载开销。

`run_tot_eval_only.py`是一个特殊设计：它不重新跑SC-ToT搜索，而是直接读取Stage 2已经落盘的搜索树文件，从树中提取各条成功路径的最终答案，用自洽性投票决定输出——这样评估搜索基线时不需要再付一轮LLM调用成本。评估结果全部写为JSON，Stage 5的上游数据就此齐全。

### 3.2.5 Stage 5: 交互式Web可视化

Stage 5的工作是把前面积累的搜索树JSON和评估结果JSON变成可以交互查看的网页。后端用Python标准库的`http.server`模块搭了一个轻量API服务（`run_stage5_api_server.py`继承`SimpleHTTPRequestHandler`，手动路由各API端点），上游依赖三个数据预处理脚本：`visualize_tot_trees.py`从搜索树JSON里提取节点、边和路径信息并精简为前端绘制所需的字段；`visualize_performance.py`汇总四个基线在两个数据集上的准确率-延迟数据；`visualize_stats.py`统计搜索过程的各类计数指标（平均深度、候选支路数、成功路径占比等）。

前端四个HTML页面各管一块功能：`tot_viewer.html`用D3.js的树布局把搜索过程画成一棵可缩放拖拽的节点图，点击任意节点可以看到该步的推理内容和评分；`performance_viewer.html`把准确率和延迟并排展示，方便一眼看出CPO相对于CoT和SC-ToT的得失；`statistics_report.html`集中呈现搜索和训练的统计数字；`index.html`是进入各页面的导航入口。为了让远程服务器上的结果可以被本地浏览器直接访问，`start_local_tunnel_and_api.ps1`用bore打了一条公网隧道，这在没有公网IP的实验环境里特别实用。

## 3.3 数据流与接口规范

五个阶段之间没有API调用，也没有共享内存，所有物料都落在磁盘上。这么做的代价是每个阶段的启动脚本都得显式读取上一阶段的输出文件，但好处也很实在：任何一个阶段出问题，不需要从头跑起，只需修好该阶段的逻辑或数据，从断点处继续即可。

具体到每个交接点：

- **Stage1 → Stage2** 传递的是`data/`下的JSONL，每行一条`{"question": "...", "answer": "..."}`。Stage 2只依赖这两个字段，所以将来如果换用第三个数据集，只要把它的原始格式洗成同样的两键结构，Stage 2不需要任何改动。
- **Stage2 → Stage3** 分两路：CPO路线走偏好数据JSONL（每行`{"prompt": "...", "chosen": "...", "rejected": "..."}`），TS-SFT路线走路径数据JSONL（每行`{"prompt": "...", "response": "..."}`）。两条训练脚本各取所需，互不干扰。
- **Stage3 → Stage4** 交给评估阶段的是LoRA权重文件，格式就是标准HuggingFace PEFT的存储约定，评估脚本加载时不需要额外的格式转换。
- **Stage2 + Stage4 → Stage5** 汇入的两路数据——搜索树和评估指标——都以JSON文件的形式交给可视化后端，前端页面通过API拉取。

整个管道靠这几层文件协议实现了解耦。修改搜索算法不会波及训练脚本（只要偏好对的字段名不变），切换评估数据集也不影响可视化（只要指标JSON的key保持一致）。

## 3.4 配置管理

管道涉及的调节项很多：ToT的束宽度、每步候选数、自洽性投票的采样次数、模型的温度参数、LoRA的秩与缩放因子、DPO的β值、训练的学习率和batch大小……如果把这些数字分散写死在各个脚本的代码深处，改一次参数要先回忆是哪个文件里的哪一行，实验记录也会变得零散难追溯。

实际的做法是把配置收敛到每个阶段脚本的**顶层交互界面**上，具体通过两层 Python 字典来实现。以 Stage 2 的 `run_stage2_pipeline.py` 为例，文件开头直接挂着 `MINIMAL_CONFIG` 和 `ADVANCED_CONFIG` 两个大字典。`MINIMAL_CONFIG` 里只放日常最常改的东西——切哪个数据集（`task: "gsm8k"` 还是 `"strategyqa"`）、跑多少条样本、最大搜索深度和束宽度——相当于该阶段的门面开关，打开脚本第一眼就能看到。`ADVANCED_CONFIG` 则收容那些调一次就很少再动的参数：评分函数的调用次数、质量过滤的最低分阈值、语义去重的相似度上限、LLM 调用的超时和重试策略等。两个字典在脚本启动时自动合并，于是改一个日常参数不需要翻到文件后半截去碰那些稳定的高级配置。

这层设计的另一个好处是和 argparse 无缝配合。每个阶段的管道入口脚本都暴露了完整的命令行参数（`--task`、`--max-depth`、`--beam`、`--max-samples` 等），命令行传入的值会直接覆盖两个字典中的默认项。实际开发中的典型工作流是：先用 `--print-config` 看一眼当前生效的完整参数集合，确认无误后去掉该 flag 正式运行；跑完一组对照实验后，把当时传入的 CLI 命令连同输出目录一起归档，就完成了实验条件的完整存档，无需单独备份配置文件。

Stage 4 的 `run_stage4_pipeline.py` 延续了同样的模式，它的 `MINIMAL_CONFIG` 控制评估任务和数据集切分，`ADVANCED_CONFIG` 管理四种基线的运行开关、基座模型路径、ToT 的搜索预算等。Stage 3 和 Stage 1 的实现也遵循同一套约定。这种"脚本即配置"的做法虽然不像独立 YAML 文件那样能把配置和数据完全分离，但减少了需要单独维护的配置层，让实验参数和调用入口始终绑定在一起——改完参数直接运行，中间没有任何翻译环节。

## 3.5 技术选型

选型上有一个明确的取舍原则：能用生态成熟的库就不从零造轮子，但控制流和数据格式的定制程度必须高到能支撑后续的灵活修改。下表是按功能层拆开的选型说明。

| 层 | 选型 | 为什么选它 |
|---|------|-----------|
| 编程语言 | Python 3.10+ | 整套大模型工具链（Transformers、PEFT、TRL）都是Python写的，没必要跨语言折腾 |
| 深度学习框架 | PyTorch 2.5.1 | HuggingFace生态的底层依赖，LoRA实现和自回归生成逻辑在PyTorch上的社区支持最完整 |
| 模型加载 | HuggingFace Transformers + PEFT | 换基座模型只需要改一行模型名，LoRA适配器加载卸载也是标准接口 |
| LLM推理 | HuggingFace Transformers + OpenAI兼容HTTP客户端 | 本地推理直接调用 `model.generate()` 走 GPU 加速；远程推理使用原生 urllib 构造 OpenAI 兼容的 `/chat/completions` 请求，与第三方 API 服务（如 SiliconFlow）无缝对接 |
| 后端API | Python 标准库 `http.server` | Stage 5 的 API 请求量不大但种类多（查树结构、查指标、查统计数据），用标准库 `SimpleHTTPRequestHandler` 手动路由即可满足需求，零额外依赖，部署时不需要安装 FastAPI/uvicorn |
| 前端可视化 | D3.js v7 | 搜索树的可视化需要自由控制节点位置、连线样式和交互逻辑，ECharts这类封装度高的库反而限制太多，D3的底层SVG操作更灵活 |
| 环境管理 | Conda | 团队成员用不同操作系统，Conda的跨平台environment.yaml可以保证各人环境一致 |
| 配置管理 | Python内联字典 + argparse | 日常切换任务只需改脚本顶层几个键值，临时覆盖走命令行，实验参数与调用入口始终绑定，无需维护额外的配置文件 |
